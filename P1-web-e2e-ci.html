Scope reminder. All targets are Jayami's own locally hosted forks (Cal.com, Documenso, Medusa, Twenty) in Docker. Security content stays at QA test-design level (expected status codes, headers, scanner config). No exploit payloads. Ideation metrics are targets to measure, not claims.

1. Goal & what this showcases

Show that Jayami can design a maintainable, fast and trustworthy UI-automation framework, not just write scripts. The ideation brief asks for: Page Object Model, API-based authentication with storageState, semantic locators, Faker-isolated data, network mocking with page.route, a Chromium/WebKit/Firefox matrix, 4-way sharding, visual regression at 393×852 / 820×1180 / 1440×900, long-name truncation, dark/light contrast, German text expansion, trace/video/console artifacts, a GitHub Pages report and a Slack alert. All four upstream repos already run their own E2E (Cal and Documenso deeply; Twenty has 7 specs; Medusa Admin has no Playwright config at all). So P1 doesn't re-test functional journeys upstream already covers. It adds what upstream lacks: cross-browser and browser-timezone matrices, visual and i18n layout checks, resilience (offline/SSE, mocked failures) and a first E2E suite for Medusa Admin.

  • Framework architecture: POM + fixtures + API auth setup projects + data factories, the same pattern applied to four very different stacks (Next.js, React Router/Remix, Vite admin SPA, React + GraphQL).
  • CI engineering: a browser matrix × 4 shards, blob-report merge, artifacts on failure, a GitHub Pages HTML report, a Slack summary, and a measured wall-clock (recorded, not claimed).
  • Visual/i18n/a11y quality: three viewports, dark/light themes, German (de) text expansion and long-name truncation, with masked dynamic regions so baselines are stable.
  • Flake discipline: no waitForTimeout; web-first assertions only; a quarantine tag and a flaky-test log whose numbers come from CI history.

6. CI workflow outline

# .github/workflows/p1-e2e.yml (outline)
on: [pull_request, workflow_dispatch, schedule(nightly)]
jobs:
  e2e:
    strategy: { fail-fast: false, matrix: { product: [cal, doc, med, tw], browser: [chromium, webkit, firefox], shard: [1,2,3,4] } }
    steps: checkout (submodules @ pinned SHA) → setup-node + cache → start product (compose/dev script per product)
           → wait-on health URL → npx playwright install --with-deps ${browser}
           → npx playwright test --project=${product}-${browser} --shard=${shard}/4 --reporter=blob
           → upload-artifact blob-report-${product}-${browser}-${shard}  (always)
  visual:          # chromium only; baselines are OS-specific, so generate them in CI (Linux container)
  merge-report:    needs: e2e → npx playwright merge-reports --reporter html ./all-blob-reports
  publish:         actions/deploy-pages (HTML report) on main
  notify:          if: failure() → Slack webhook (secret) with pass/fail/flaky counts + report URL
# PR gate: chromium × 4 shards on PR; full browser matrix nightly (cost control; record the decision in DECISIONS.md)

  • trace: "on-first-retry", video: "retain-on-failure", screenshot: "only-on-failure", plus the console log attached by the consoleGuard fixture.
  • Merged HTML report on GitHub Pages; JUnit XML for the GH test summary; visual diff images (expected/actual/diff) inside the report.
  • Run metrics captured from CI (wall-clock per shard, total, retries, flaky count). These go into the README only after they have been measured.

8. README checklist

  • Architecture diagram + folder tree; why the tests live outside the products.
  • One-command local run per product, and the exact product SHA tested.
  • Coverage table: test ID → primitive → upstream depth → why it is not a duplicate.
  • Measured CI numbers (sharded vs unsharded wall-clock, flaky rate over N runs). No targets presented as results.
  • Visual baseline policy (who updates, tolerance and why), quarantine policy, and links to the GH Pages report and a sample failing trace.
